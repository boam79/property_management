> 상태: **설계 확정 · 구현 보류** (2026-08-08)  
> 목적: 나중에 이 문서를 기준으로 PoC → 본구현을 진행한다.  
> 관련: 구매이력은 이미 `apps/purchase-desktop` 로컬 앱으로 이전됨.

---

## 1. 배경과 목표

현재 자산관리는 Next.js + Supabase(클라우드 DB) 중심이다.  
비용 절감과 본사 PC 중심 운영을 위해, **관리·본 데이터는 설치형 PC**, **QR 스캔은 지금과 같은 웹 URL** 로 유지하는 하이브리드로 전환한다.

### 확정된 요구사항

| # | 요구 | 결정 |
|---|---|---|
| 1 | 설치 PC | **1대만** |
| 2 | 이미 등록된 QR을 폰으로 재스캔 | **폰에도 자산 정보 표시** |
| 3 | 클라우드 | **비우는 것이 목적**(비용 절감) — 단, 완전 0은 불가(아래 참고) |
| 4 | QR 인식 방식 | **현재와 동일** (HTTPS `/q/[token]`) |
| 5 | 폰 조회 요약 필드 | **6개만** (섹션 4) |

### 비용 절감에 대한 정리

- **방향은 Supabase 비용 절감이 맞다.** 자산 본문·관리 트래픽을 PC로 옮기고 클라우드에는 짧은 조회 요약(+잠깐의 수신함)만 남긴다.
- **완전 무료·DB 완전 삭제**는 아님. Auth, QR용 웹 호스팅, **조회용 요약 테이블**은 남는다.
- “클라우드를 비운다” = **본창고를 비운다** (대용량 assets/이력 등). 폰 조회용 최소 조각은 유지.

### 왜 클라우드를 완전 0으로 못 하는가

폰은 PC 하드디스크를 직접 볼 수 없고, QR은 인터넷 URL로 열린다.  
**폰에 자산 요약을 보여 주려면** 어딘가에 원격으로 읽을 수 있는 최소 데이터가 필요하다.

## 2. 권장 아키텍처: H1-Lite

코드명: **수신함(Inbox) + 조회 카드(Lookup)**

```
[폰 카메라]
    │  HTTPS /q/{token}  (지금과 동일)
    ▼
[얇은 웹]
    ├─ 미등록 QR → 현장 입력 → sync_inbox(임시)에만 저장
    └─ 등록됨   → qr_lookup(요약 6개)만 읽어 표시

[PC 설치 앱 1대]  ←── 본 DB (SQLite 등), 관리 UI 전부
    │
    ├─ 매일 1회(또는 수동) : inbox pull → 로컬 merge
    ├─ 성공 확인 후       : inbox 해당 건 DELETE
    └─ 로컬 자산 변경 시  : qr_lookup upsert (요약만)
```

| 위치 | 역할 |
|---|---|
| **PC** | 자산 전문, CRUD, 임포트, 대시보드, QR 배치 원장, 백업 |
| **클라우드 inbox** | 신규/현장 등록 대기열 — 싱크 후 **비움** |
| **클라우드 lookup** | QR당 요약 1행(6필드) — **상시 유지(작음)** |
| **웹** | QR 접수·조회만 (관리 화면은 단계적으로 제거) |

### 비권장 대안

| 안 | 이유 |
|---|---|
| PC를 터널로 열어 폰→PC 직접 조회 | PC 끄면 QR 사망, 망/보안 부담 |
| 클라우드 완전 삭제 + 폰은 “PC에서 보세요”만 | 요구사항 2 위반 |
| 지금처럼 전부 Supabase | 비용 절감 목표와 반대 |

## 3. 데이터 흐름

### 3.1 신규 등록 (미사용 QR)

1. 폰에서 `/q/{token}` 열기 → 로그인(필요 시) → 자산 입력  
2. 웹은 **본 assets 테이블이 아니라 inbox**에 저장  
3. PC 앱이 pull → 로컬 DB에 자산·QR 연결 반영  
4. 로컬 커밋 성공 후 inbox 건 삭제  
5. PC가 `qr_lookup`에 요약 6개 upsert  
6. 이후 같은 QR 재스캔 → lookup만으로 폰 표시

### 3.2 재조회 (이미 등록된 QR)

1. 폰 → `/q/{token}`  
2. 웹은 `qr_lookup`만 조회해 6개 필드 표시  
3. (전환 후) 웹 “상세·수정” 링크는 PC 앱 안내로 대체

### 3.3 PC에서 수정

1. 로컬 DB 수정  
2. 요약에 영향 있는 필드 변경 시 `qr_lookup` upsert  
3. 클라우드 본문 테이블은 쓰지 않음

### 3.4 일일 싱크

- 트리거: 앱 시작 시 “24시간 경과” 또는 Windows 작업 스케줄 / 수동 버튼  
- **절대** pull 성공·로컬 검증 전에 cloud DELETE 하지 않음  
- 실패 시 재시도, inbox 유지

## 4. 조회용 요약 필드 (확정)

폰에 보여줄 **6개만**:

1. QR 표시코드 (`display_code`)  
2. 자산번호 (`asset_no`)  
3. 자산명 (`name`)  
4. 구분 (`asset_type`: 일반 / IT / 의료)  
5. 상태 (`status`: 사용중 / 재고 / 수리 / 폐기)  
6. 위치 (`location`)

### 요약에 넣지 않음 (PC 본문만)

- 사용부서, 담당자, 카테고리  
- 시리얼, 제조사, 모델  
- 구매일, 구매금액, 메모  
- 감사·수정 이력 등

(현행 `/q` 등록 완료 화면과 동일한 정보량.)

## 5. 클라우드에 남길 것 / 비울 것

### 남김 (최소화)

- Auth (로그인)  
- `qr_lookup` (또는 동등 테이블/뷰)  
- `sync_inbox` (짧게 쌓였다가 비움)  
- QR 토큰 해석에 필요한 최소 메타(미사용 QR 존재 여부 등 — 설계 시 확정)

### 이관 후 비움·축소 대상

- `assets` 등 **본문 대량 보관**  
- 장기 감사로그·통계용 히스토리를 클라우드에 둘 필요 없음(정책에 따라 PC만)  
- 웹 관리 UI가 의존하던 상시 클라우드 읽기

### 초기 이관

1. 현재 Supabase 자산·QR → **1회** PC 로컬로 export/import  
2. lookup 6개 일괄 생성  
3. 본문 클라우드 축소/삭제 전에 **로컬 백업 검증**  
4. 검증 후 본문 DROP 또는 truncate (실행은 별도 승인)

---

## 6. 안전장치

1. **삭제 순서**: 로컬 커밋 성공 → ack → 그다음 inbox DELETE  
2. **lookup 불일치 방지**: 로컬 저장 성공 후에만 lookup upsert  
3. **PC 장애**: 로컬 DB 정기 백업(구매이력 앱과 동일 패턴). lookup만으로는 복구 불가  
4. **PC 1대 전제**: 다중 PC 동기화는 범위 밖. 나중에 필요하면 문서 개정  
5. **롤백**: 본문 클라우드 삭제 전 스냅샷·수출본 보관

## 7. 구현 단계 (나중에 실행)

구현 착수 시 아래 순서를 기본으로 한다. **지금은 문서만 커밋.**

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **P0 PoC** | inbox 1건 등록 → PC pull → 로컬 저장 → inbox 삭제 → lookup으로 폰 재조회(6필드) | 수동 시나리오 통과 |
| **P1** | PC 자산 목록·수정, lookup 동기화 | PC에서 CRUD 후 폰 요약 갱신 |
| **P2** | 웹 관리 UI 축소 (QR만 남김) | 관리 메뉴 PC로 안내 |
| **P3** | 기존 데이터 이관 + 클라우드 본문 비우기 | 용량·비용 확인, 백업 검증 |
| **P4** | 일일 자동 싱크·백업·업데이트 | 운영 체크리스트 |

기술 후보: 구매이력과 같이 **Tauri + SQLite** 확장 또는 통합 앱. PoC에서 확정.
